|---|---|---|---|
| Document processing state | `extracted.document.status` (internal DB column: `'registered'`/`'processing'`, G5 lock state) | `status_badge` / `DocumentStatusBadge` (computed, user-facing: `'Processing'`/`'Extracted'`/`'Reconciling'`/`'Retrying'`/`'Failed'`/`'Reconciled'`) | Same underlying concept ("what state is this document in"), two entirely different vocabularies and cardinalities (2 internal values vs. 6 display values). `documentStatus.ts:29-39` explicitly documents the tension and resolves it — this is a known, already-reasoned-through disambiguation, not an oversight, but still worth flagging per this task's own instructions. |
| NetSuite bill/document number column | `tranid` (live Fabric Lakehouse, engineer-confirmed) | `bill_document_number` (SQLite test fixture, `scripts/netsuiteVendorBillFixture.mjs:17`) | Explicitly called out as a real naming mismatch in `src/lib/deterministicMatching.ts:12-16` — the fixture's name is "this project's own inference," not the real column name. Two code paths (`findReferenceRowByDocNumber`'s Fabric branch vs. SQLite branch, `deterministicMatching.ts:79-120`) read genuinely different column names for the same concept. |
| NetSuite transaction PK | `entity`/no separate PK named in captured columns (live) | `transaction_id` (fixture PK, `netsuiteVendorBillFixture.mjs:16`) | Fixture invents both a PK name and shape not confirmed to exist on the live table — same caveat as above. |
| NetSuite bill amount | `total` (live) | `amount` (fixture) | Same mismatch pattern as `tranid`/`bill_document_number`. |
| CCC repair-order table itself | "equivalent CCC tables" (per ARCHITECTURE.md D9/D-M, unconfirmed name) | `bronze_ccc_repair_order` (this project's own placeholder, `cccRepairOrderFixture.mjs:2-8`) | Unlike the NetSuite case, there is no engineer-confirmed live name at all here — the placeholder is the ONLY name that exists anywhere in source.
