**Module** — Claude Sonnet 4.6 client
**ID** — M-023
**Layer** — pipeline
**Primary Responsibility** — `AIClient` implementation for Claude Sonnet 4.6 via Azure Foundry (streaming). **Confirmed the actual active extraction primary** — `active_provider.json`'s `provider_chain[0]`, resolved by `client_factory.get_ai_client()` with no argument.

**Inputs** — `ClaudeSonnetClient(config, transport=None)`; `generate(prompt, ...)`; `generate_with_file(pdf_path, prompt)` — **`prompt` parameter is accepted but ignored**; always sends its own embedded `EXTRACTION_PROMPT`.

**Outputs** — `AIResponse` with `parsed_json` built by this client's own `_build_schema()`. **As of 2026-07-24 (see Known Fragility below), each row's `line_confidence` is the model's own genuine, requested per-row confidence value** (parsed via `_parse_confidence()`), falling back to `FALLBACK_LINE_CONFIDENCE = 0.40` — below the `0.60` validation threshold — only when the model omits it or returns something unparseable/out-of-range.

**Public Interface**
- `generate(...) -> AIResponse`, `generate_with_file(pdf_path, prompt) -> AIResponse`
- Private: `_build_client()`, `_real_text_call()`, `_real_file_call()` (streaming — `client.messages.stream()` + `get_final_message()`, required because a single whole-document call can run long enough to risk a non-streaming read timeout), `_detect_truncation()`, `_pdfplumber_row_count()`, `_rows_to_invoices()`, `_map_columns()`, `_pick_cleanest_column()`, `_row_to_invoice()`, `_looks_like_invoice_number()`, `_fallback_invoice_number()`, `_fallback_amount()`, `_to_float()`, `_build_schema()`, `_try_parse_json()`, `_salvage_rows_from_truncated_json()`, `_clean_error()`

**Error Behaviour** — Never raises out of `generate_with_file()`/`generate()` — every failure path converts to a clean `AIResponse(success=False)`. Truncation is explicitly *detected* (not just salvaged) via `_detect_truncation()` and treated as an immediate fallback signal, not retried — confirmed: a systematically truncated response would very likely truncate again on retry, so `generate_with_file()` returns failed immediately rather than looping.

**Known Fragility — the central finding of this session's confidence-fabrication investigation**
- **FIXED 2026-07-24 — confidence fabrication (R-001).** `ROW_CONFIDENCE = 0.75` was hardcoded and applied to every row regardless of actual legibility (`"line_confidence": ROW_CONFIDENCE`), and `EXTRACTION_PROMPT` never asked the model for confidence at all. Confirmed with live data at the time: 100% of 1,510 (local) + additional (Azure SQL) Bronze rows tagged `claude_sonnet/claude-sonnet-4-6` showed exactly `0.75`, zero variance. **Fix:** `EXTRACTION_PROMPT` now explicitly instructs the model to include a per-row `"confidence"` field (0.0-1.0) with calibration guidance (0.9+ only if unambiguous; lower for unclear handwriting/scan quality, guessed invoice numbers, uncertain column mapping). `_row_to_invoice()` now reads `row.get("confidence")` via a new `_parse_confidence()` helper and uses the model's real value; `ROW_CONFIDENCE` (0.75) is no longer used for row-level confidence. If the model omits the field or returns something unparseable/out-of-range, it falls back to `FALLBACK_LINE_CONFIDENCE = 0.40` — deliberately below the `0.60` threshold, so a missing/untrustworthy signal routes to human review rather than silently passing (RULE-10). **Verified against 2 real sample PDFs post-fix:** `ASTCollex0526.pdf` (202 rows) came back uniformly at `0.99` — plausible for a clean, unambiguous digital-text PDF, but on its own does not distinguish "genuine high confidence" from "another flat constant"; `KSI_Noakers_053126.pdf` (69 rows) came back with two distinct values (`0.93` and `0.95`), which combined with the cross-document difference (0.99 vs 0.93/0.95) confirms the value is now genuinely model-elicited rather than a hardcoded constant — a true constant would not vary at all, across rows or documents. **Confirmed 2026-07-24 (retry with a 10-minute window and per-chunk streamed progress logging):** `Very_Dirty_Scanned_Reconciliation.pdf` extraction completed in 148.5s — the prior attempt's apparent hang was genuine model latency for this harder document colliding with an external 5-minute tool timeout (compounded by stdout buffering hiding how much progress had actually been made), not a stuck API call; the retry showed continuous, gap-free token arrival (~1-1.5s between chunks) for the full 148.5s. Confidence on this document ranged `0.35-0.60` across 132 rows (6 distinct values, including intra-document variance), sharply lower than the clean-PDF results above (`0.99`/`0.93-0.95`) — this is the positive evidence that was missing before: confidence genuinely tracks real document difficulty rather than landing on a new fixed habitual default. Under `validate_invoice()`'s `< 0.60` check, 129 of these 132 rows would correctly route to human review (only 3 rows at exactly `0.60` pass) — a concrete demonstration of the fix's protective effect on a genuinely hard document, versus 0/132 under the old hardcoded `0.75`. Only Claude Sonnet (M-023) was fixed this pass — `GeminiClient` (M-025) and `MistralClient` (M-026) have the identical bug, deliberately left untouched (dormant, not the active provider). See `discovery/RISK_REGISTER.md` R-001 ("Partially mitigated").
- **FIXED 2026-07-24 — missing totals-row exclusion (R-002).** Neither the prompt nor `_row_to_invoice()`/`_rows_to_invoices()` filtered out a summary/total row, unlike `pdfplumber_fallback.py`'s explicit keyword skip. **Fix:** added `_is_totals_row()` (checks the final `invoice_number` against `TOTALS_ROW_KEYWORDS = ("total", "balance", "subtotal")`, same keywords as `pdfplumber_fallback.py:_extract_invoice_row()`) — a matching row is dropped (`_row_to_invoice()` returns `None`, filtered out in `_rows_to_invoices()`) rather than ingested as an invoice line. `EXTRACTION_PROMPT` also now explicitly instructs the model not to report a grand-total/subtotal/balance-forward row as an invoice line, as defense in depth alongside the code-level filter. GeminiClient/MistralClient deliberately left untouched — same bug, still dormant. See `discovery/RISK_REGISTER.md` R-002 ("Partially mitigated"), `discovery/INVARIANT_CATALOGUE.md` IC-20.
- **Column mapping via `_map_columns()`'s keyword lists**, with a value-based fallback for `invoice_number`/`outstanding_amount` only (`_fallback_invoice_number`, `_fallback_amount`) — narrower than `VISION_PROMPT`'s instruction to semantically reason about any unfamiliar column for every field. Not in scope for this pass.
