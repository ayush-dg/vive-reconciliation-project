**Module:** ExceptionVendorDetailView
**ID:** M-074
**Layer:** component
**Primary Responsibility:** Client-side two-pane master-detail UI for one vendor's exceptions — filterable list on the left, full detail (statement/ERP comparison, NetSuite record drill-down, note + resolve/flag/skip actions, prev/next paging) on the right.

**Inputs (Props):** `{ vendorSlug: string; initialRows: VendorExceptionRow[]; initialSelectedId: string | null }` (types from `@/lib/exceptionsList`, out-of-scope M-019).
**Outputs (Rendered UI + Side Effects):**
- Renders a topbar with a back-link to `/exceptions` and humanized vendor name (`humanizeVendorSlug`, M-010); a left pane with filter tabs (All/Missing/Mismatch), a resolve-progress bar (`resolvedCount`/`total` computed from ALL `rows`, not the filtered subset), and a scrollable list of exception rows; a right pane showing the selected exception's full detail — invoice/vendor/period/amount field grid, conditional ERP-amount/difference fields (only when `detail.amountMismatch` is present), a computed "why this is an exception" explanation (`whyText`), a CCC-corroboration panel (present/absent states), a collapsible NetSuite record panel (curated `HIGHLIGHT_FIELD_ORDER` fields first, then an expandable full raw field dump sorted alphabetically), a note textarea, and Resolve/Flag-for-vendor/Skip action buttons + prev/next pager.
- `loadDetail(id)`: `GET /api/exceptions/{id}` (M-049) — on success sets `detail` and seeds `noteDraft` from `detail.note`; **silently does nothing on failure** (no `else`/`catch` branch sets any error state) — see Known Fragility.
- `refreshRows()`: `GET /api/exceptions/vendor/{vendorSlug}` (M-050) — sets `listLoadError` on failure, shown via `InlineLoadError` (M-081).
- `applyAction(status)`: `PATCH /api/exceptions/{selectedId}` (M-049) with `{ status, note: noteDraft }` — on success, updates `detail` from the response and calls `refreshRows()`; **on failure, silently does nothing** (no error toast/state) — see Known Fragility.
- Two `useEffect`s: one resets `selectedId` to the filtered set's first row when `filter` changes and the current selection falls outside it; one calls `loadDetail(selectedId)` whenever `selectedId` changes.
**State Consumed:** None from shared stores — all state (`rows`, `filter`, `selectedId`, `detail`, `detailLoading`, `listLoadError`, `noteDraft`, `actionPending`, `netsuiteOpen`, `rawOpen`) is local `useState`. Does not use `useToast` (M-083) — unlike M-068/M-070/M-076, this component has no toast feedback for action success/failure.
**Public Interface:** `export default function ExceptionVendorDetailView({ vendorSlug, initialRows, initialSelectedId }: { vendorSlug: string; initialRows: VendorExceptionRow[]; initialSelectedId: string | null })`.
**Error Behaviour:** `[NOTABLE]` Unlike every other data-mutating component in this app (M-068, M-070, M-076, which all show error toasts on failed POST/PATCH), `loadDetail` and `applyAction` here have **no failure feedback at all** — a failed `GET /api/exceptions/{id}` leaves `detail` unchanged (stale or null) with no error indicator, and a failed `PATCH` (resolve/flag/skip) leaves the UI looking like nothing happened, with `actionPending` correctly reset in the `finally` block but no toast or inline error to tell the user the action didn't take effect. Only `refreshRows()` (the list-level refresh) has visible error handling via `InlineLoadError`.
**Known Fragility:** The silent-failure gap above is the single biggest fragility — a user clicking "Mark resolved" against a network blip would see the button re-enable with no indication the resolve didn't happen, and might assume it succeeded. `whyText()` hard-codes the two known exception categories (`amount_mismatch`, `not_posted`) via `if`/fallback — a third category added upstream would fall through to the generic "no matching bill" text even if inappropriate. `HIGHLIGHT_FIELD_ORDER` is a fixed, hand-picked list per its own comment ("kept short and generic...since which custom fields a live NetSuite row actually carries varies per vendor") — fields not in this list never appear in the highlighted grid, only in the full raw dump.
**Change Impact:** Changes to `ExceptionDetailData`/`ExceptionStatus` shape (out-of-scope lib `exceptionDetail.ts`) affect rendering and the PATCH payload shape. Changes to `/api/exceptions/{id}` (M-049) or `/api/exceptions/vendor/{slug}` (M-050) response shapes break this component silently in the failure case (no visible error) or overtly in the success case (type mismatch). Changes to `humanizeVendorSlug` (M-010) affect vendor-name display here, M-072, and M-076.
**Callers:** M-073 (ExceptionVendorDetailPage) renders this.
**Calls:** fetch `GET /api/exceptions/{id}` (lines 76, → M-049); fetch `PATCH /api/exceptions/{id}` (line 112, → M-049); fetch `GET /api/exceptions/vendor/{vendorSlug}` (line 95, → M-050); M-010 (`vendorDisplay.ts` `humanizeVendorSlug`, lines 143, 145, 223, 240).
**Renders:** M-081 (InlineLoadError, conditional on `listLoadError`).
**Integration Points Used:** None (fetches internal API routes only).
