**Module:** batchUploadSequencing
**ID:** M-084
**Layer:** module (pure function, client-side)
**Primary Responsibility:** Sequences a multi-file batch upload's register+extract cycle — single-file stays fire-and-forget (byte-for-byte pre-ENH-001 behavior), a 2+-file batch awaits each file's full cycle before the next file's registration begins, so no two extractions are ever in flight simultaneously.
**Added:** 2026-09-06, SPRINT-001 BCE refresh (ENH-001 Task 2.2 — created 2026-09-04, contract entry deferred to this refresh per sprint doctrine).

**Inputs:** `runBatchUploadSequenced(files: TFile[], registerFile: (file: TFile) => Promise<BatchRegisterResult>, extractDocument: (documentId: string) => Promise<void>)` — a generic list of files plus two caller-injected async callbacks. `BatchRegisterResult = { ok: boolean; duplicate: boolean; documentId: string | null }`.
**Outputs:** `Promise<void>` — resolves once every file has been processed (registered, and extracted where applicable). No return value; all UI-visible effects (progress rows, toasts) are driven by the injected callbacks themselves (owned by M-070), not by this module.
**Public Interface:** `export async function runBatchUploadSequenced<TFile>(files, registerFile, extractDocument): Promise<void>`; `export type BatchRegisterResult`.
**Error Behaviour:** Never throws for a single file's failure — a registration failure (`ok: false`), a duplicate (`ok: true, duplicate: true`), or a missing `documentId` are all treated as "skip, continue to the next file," matching a registration failure's own skip-not-fatal policy. An extraction failure (the injected `extractDocument` callback rejecting) is caught internally (`try { await extractDocument(documentId) } catch { /* symmetric to a registration failure */ }`) so one file's extraction throwing never aborts the batch — deliberate, since the caller (`extractAndTrack` in M-070) already resolves its own row to a terminal state internally and is not expected to reject in practice, but this module doesn't assume that.
**Known Fragility:** None identified — this module has no internal state, no I/O of its own, and no shared mutable data; correctness reduces entirely to whether the injected callbacks behave as documented. Its single-file "fire-and-forget" branch (`void runExtraction()`, not awaited) means a caller that doesn't separately track completion has no way to know when that extraction actually finishes — by design (matches pre-ENH-001 UX), but worth remembering if this module is ever reused somewhere that needs completion visibility for the single-file case too.
**Change Impact:** Sole caller is M-070 (`UploadForm.tsx`, `handleSubmit`). A change to `BatchRegisterResult`'s shape or to the sequencing policy (e.g., making multi-file batches concurrent) would need to be re-verified against `scripts/test_batch_upload_sequencing.sh` (12/12 assertions, the only test coverage of this module's actual sequencing guarantee — no Playwright test exercises this module directly, only its effects via `UploadForm.tsx`).
**Callers:** M-070 (`UploadForm.tsx:handleSubmit`) only.
**Calls:** None directly — `registerFile`/`extractDocument` are injected by the caller (M-070), which internally reaches M-044 (register) and M-046 (extract) via `fetch`. This module has zero import-level dependencies of its own beyond its own type definitions.
**Integration Points Used:** None (no direct fetch/DB access — pure orchestration over injected callbacks).
