**Module:** login/actions.ts
**ID:** M-054
**Layer:** route
**Primary Responsibility:** Next.js Server Actions implementing the login form's credential verification + session-cookie issuance (`loginAction`, bound via `useActionState`) and the sidebar logout action (`logoutAction`).

**Inputs:**
- `loginAction(_prevState: LoginState, formData: FormData): Promise<LoginState>` — called by React's `useActionState` (M-063, `LoginForm.tsx`), so `_prevState` is the prior action-state (unused) and `formData` is the submitted login form. Reads `username` (`String(formData.get('username') ?? '').trim()`) and `password` (`String(formData.get('password') ?? '')`, not trimmed).
- `logoutAction(): Promise<void>` — no inputs; invoked via a `<form action={logoutAction}>` in M-082 (Sidebar.tsx).
**Outputs:**
- `loginAction`: on validation/auth failure, returns `LoginState = { error: string }` back to the calling component (React re-renders the form with that error) — `{ error: 'Enter your username and password.' }` if either field is empty/whitespace-trimmed-empty, or `{ error: 'Invalid username or password.' }` for both "no such user" and "wrong password" (deliberately identical message, per the code's own comment, to avoid disclosing which one failed). On success: sets the `vive_session` cookie (via `cookies()` from `next/headers`, `sessionCookieOptions()` from M-004) and calls `redirect('/home')` — `redirect()` throws a special Next.js control-flow signal, so `loginAction` never actually returns a value on the success path; the function's return type (`LoginState`) is only meaningful on the failure paths.
- `logoutAction`: deletes the `vive_session` cookie and calls `redirect('/login')` — same non-returning control-flow pattern; return type is `Promise<void>` but the function never completes normally on its only code path.
**Public Interface:**
`export type LoginState = { error: string | null }`
`export async function loginAction(_prevState: LoginState, formData: FormData): Promise<LoginState>`
`export async function logoutAction(): Promise<void>`
(File begins with `'use server'` — both exports are Next.js Server Actions, not HTTP route handlers; no exported GET/POST.)
**Error Behaviour:** No try/catch in either action. `findUserByUsername` (M-001) can throw (e.g. Fabric pool connection failure in non-SQLite mode) — unhandled here, which in a Server Action surfaces as an unhandled rejection to the Next.js framework, not a `LoginState` error the form can display gracefully; NOT DETERMINABLE FROM SOURCE exactly what UI the user sees in that case (framework-level error boundary, likely M-066/`(app)/error.tsx` or a generic error page, not this module's own code). `signSessionToken` (M-004) throws if `SESSION_SECRET` is unset — same unhandled-rejection outcome. `redirect()` itself is implemented by Next.js via a thrown special-purpose error that the framework catches internally to perform the actual redirect — this is expected/intentional, not a bug, but means neither action's "success" path is reachable by normal `return` — a future engineer adding code after a `redirect()` call (e.g. logging) would find it never executes.
**Known Fragility:** [NOTABLE] The identical error message for "no such user" vs. "wrong password" is a deliberate anti-enumeration measure per the inline comment — a future engineer "fixing" this to be more specific (e.g. splitting into distinct messages for debugging convenience) would reintroduce a username-enumeration vector. `password` is read without `.trim()` while `username` is trimmed — intentional-looking (passwords may legitimately contain leading/trailing spaces) but easy to "fix" inconsistently by a future engineer who assumes both fields should be treated the same way, which would change password-matching behavior for any password containing whitespace. `verifyPassword` (M-001) uses `crypto.timingSafeEqual` — a future refactor to a simpler `===` comparison would reintroduce a timing side-channel, a class of regression this module currently guards against but doesn't self-document at this layer (the guard lives in M-001, not here).
**Change Impact:** `loginAction` is the sole action bound to M-063's `useActionState` — its `LoginState` return shape (`{error: string|null}`) is exactly what that form component destructures for its error display; changing the field name or type breaks that binding. `logoutAction` is bound identically from M-082 (Sidebar.tsx)'s logout form. Both actions' cookie-setting depends on M-004's `SESSION_COOKIE_NAME`/`sessionCookieOptions`/`signSessionToken` staying consistent with what M-043 (proxy.ts) reads on every subsequent request — a mismatch here (e.g. a different cookie name) would break the entire auth shell, not just login.
