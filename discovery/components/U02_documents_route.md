**Module:** api/documents/route.ts
**ID:** M-044
**Layer:** route
**Primary Responsibility:** Lists all registered documents with their computed status badge (GET), and registers a new PDF statement upload against a legal entity with dedup-by-content-hash handling (POST).

**Inputs:**
- `GET`: no params, no query, no body.
- `POST(request: Request)`: body is `multipart/form-data` (`FormData`), parsed via `request.formData()`. Expected fields: `file` (must be a `File` instance), `legalEntityId` (string, coerced via `String(formData.get('legalEntityId') ?? '')`). Validation performed in-handler, in order: form-data parse must succeed; `file` must be a `File`; file must "look like" a PDF (`file.type === 'application/pdf'` OR filename ends in `.pdf`, case-insensitive); file size must be <= 50 MB (`MAX_FILE_BYTES = 50 * 1024 * 1024`); `legalEntityId` must match one of `LEGAL_ENTITIES` (M-042, data read not a call).
**Outputs:**
- `GET` 200: `{ documents: ApiDocument[] }` — each `ApiDocument` is the snake_case wire shape from M-011 (`document_id`, `content_sha256`, `legal_entity_id`, `vendor_id`, `vendor_slug`, `statement_period`, `status`, `status_badge: {badge,label}`, `upload_timestamp`, `original_filename`, `open_exception_count`).
- `POST` 400: `{ error: string }` for: form-data parse failure ("Expected multipart/form-data."), missing/non-File `file` ("Select a PDF statement."), non-PDF file ("PDF files only."), file over 50MB ("File exceeds the 50 MB limit."), or invalid/missing `legalEntityId` ("Select a legal entity.").
- `POST` 201 (new document) or 200 (duplicate, `duplicate: true`): `{ document: ApiDocument, duplicate: boolean, legalEntityMismatch?: boolean }`. Status is `201` unless `duplicate` is true, in which case it's `200` even though the response body still describes the (pre-existing) document.
**Public Interface:**
`export async function GET(): Promise<NextResponse>`
`export async function POST(request: Request): Promise<NextResponse>`
**Error Behaviour:** `GET` has no try/catch and cannot itself fail on valid input — if `listDocumentsWithStatusBadge()`/`computeDocumentStatus()`/`getOpenExceptionCount()` (all M-011/M-012) throw (e.g. SQLite unavailable, or Fabric mode since M-011 only supports SQLite and throws otherwise), the exception is unhandled -> Next.js's default 500. `POST` wraps only the `request.formData()` call in try/catch (400 on parse failure); all subsequent validation is explicit `if` checks returning 400, not exceptions. `registerDocument` (M-011) can throw on a non-unique-constraint DB error (it only recovers from `UNIQUE constraint failed` errors); such a throw is unhandled here -> 500.
**Known Fragility:** [NOTABLE] The PDF-signal check (`file.type === 'application/pdf' || file.name...endsWith('.pdf')`) is documented in-code as a deliberate fix for a prior defect where empty MIME type "failed open" (accepted anything) — a future refactor that reverts to `file.type && file.type === 'application/pdf'` would silently regress to accepting non-PDFs when the client omits MIME type. `legalEntityId` validation depends on `LEGAL_ENTITIES` (M-042) staying in sync with whatever the Upload UI (M-070) offers — M-042's own doc comment says this is a placeholder list, not sourced from VIVE's real legal entity structure, and is a flagged open gap. Duplicate-detection is by raw content SHA-256 (via M-011), so a byte-for-byte identical re-upload under a different legal entity produces `legalEntityMismatch: true` but is otherwise silently discarded — no new document is created and the mismatch is not surfaced as an error status, only as a response field the caller must check.
**Change Impact:** Sole data source for the Upload screen's list (M-070, GET) and the Home screen's document tiles (M-068, GET). The 201 vs 200 status-on-duplicate convention and the `duplicate`/`legalEntityMismatch` fields are relied on by any UI consuming POST — changing them changes upload-success/duplicate-warning UX. Changing `MAX_FILE_BYTES` changes the documented 50MB Upload-screen limit referenced in the code comment. Downstream of M-011/M-012 for both list contents and status-badge computation — any bug there surfaces here unfiltered (no defensive handling in this route beyond form validation).
**Callers:** M-068 (HomeView.tsx, fetch GET), M-070 (UploadForm.tsx, fetch GET + POST upload)
