**Module:** ToastProvider (+ useToast hook)
**ID:** M-083
**Layer:** store
**Primary Responsibility:** Thin React subscriber over the framework-agnostic `toastStore` (M-009) — renders the bottom-right toast container and exposes the `useToast()` hook other client components use to fire success/error toasts.

**Inputs (Props):** None (`ToastProvider` takes no props).
**Outputs (Rendered UI + Side Effects):** `ToastProvider`: on mount, subscribes to `toastStore` via `toastStore.subscribe(setToasts)` in a `useEffect` (unsubscribes on unmount, returned cleanup); if `toasts.length === 0` renders `null`; otherwise renders `<div role="status" aria-live="polite" data-testid="toast-container" className="toast-container">` with one `<div data-testid="toast-{kind}" role="alert">` per toast, each with a dismiss (`×`) button calling `toastStore.dismiss(toast.id)`. `useToast()`: returns `{ showSuccess, showError }`, each a thin wrapper calling `toastStore.add('success'|'error', message)`.
**State Consumed:** Reads/writes `toastStore` (M-009, `@/lib/toastStore`) at lines 9 (initial `getToasts()`), 11 (`subscribe`), 20 (`add` via `showSuccess`), 30 (`add` via `showError`). `toastStore` is a module-level singleton (`export const toastStore = createToastStore()`), not a React context — meaning any client code importing `toastStore` directly (bypassing `useToast`) could also mutate it, though no such usage was found in this session's modules (all use `useToast()`).
**Public Interface:** `export default function ToastProvider()`; `export function useToast()` returning `{ showSuccess: (message: string) => string; showError: (message: string) => string }` (return type of `toastStore.add` is the toast's `id: string`, per M-009's source).
**Error Behaviour:** N/A for this component's own logic — it has no fetches. Individual toasts auto-dismiss after `DEFAULT_AUTO_DISMISS_MS = 5000` (5s), per `toastStore`'s own internal timer logic (M-009), not implemented in this file.
**Known Fragility:** `[NOTABLE]` `toastStore` is a single app-wide singleton instantiated once at module load (`export const toastStore = createToastStore()` in M-009) — since `ToastProvider` is mounted once in M-064 ((app) layout), all toasts across Home/Upload/Exceptions/Document Detail share one stream; this is by design ("App-wide singleton — one toast stream shared across the (app) layout" per M-009's comment) but means two unrelated actions firing toasts in quick succession could stack up to 5+ visible toasts simultaneously with no cap enforced anywhere in this component. If `ToastProvider` were ever mounted twice (e.g., accidentally nested), both instances would subscribe to the same singleton and each render its own toast container, duplicating every toast visually.
**Change Impact:** `useToast()`'s signature/behavior is depended on by M-068, M-070, M-076, and M-079 — a breaking change to its return shape breaks all four. `ToastProvider` itself is only mounted in M-064; if removed from there, `useToast()` calls elsewhere would still add toasts to the store but nothing would render them (silent, no error).
**Callers:** M-064 ((app) layout) renders `<ToastProvider />`. `useToast()` (the hook) is called by M-068, M-070, M-076, M-079.
**Calls:** M-009 (`toastStore.ts`, at ToastProvider.tsx:9, 11, 20, 30).
**Integration Points Used:** None (fetches internal API routes only) — N/A, no fetch.
