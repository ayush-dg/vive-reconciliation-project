**Module:** api/matching/run-batch/route.ts
**ID:** M-053
**Layer:** route
**Primary Responsibility:** Scheduled-batch entry point that runs matching across every eligible document (any document with silver statement lines that have neither a Match nor an Exception yet), exposed for an external scheduler (n8n, IP-005) to invoke since this build has no live internal cron/timer.

**Inputs:** `POST()` — no params, no query, and the request body is not read at all (the handler signature takes zero arguments). Any body an external caller sends is entirely ignored — no validation, no auth token check inside this handler itself (auth is whatever `proxy.ts`/M-043 enforces at the routing layer, if this path is even matched by it — NOT DETERMINABLE FROM SOURCE within this route whether `/api/matching/run-batch` is excluded from the auth matcher the way `/api/health` explicitly is; per M-043's matcher regex it is NOT excluded, so an external n8n caller must present a valid session cookie, which is an unusual requirement for a machine-to-machine integration endpoint — [NOTABLE] potential mismatch between this route's stated purpose (external scheduler calls it) and the session-cookie auth it inherits from M-043).
**Outputs:** 200 only: `ScheduledMatchingBatchResult` — `{ processed: string[], skipped: string[] }` where `processed` is document IDs that were successfully matched (lock acquired, `matchDocument` completed) and `skipped` is document IDs whose lock was already held by a concurrent invocation (manual per-document trigger via M-047, or another batch run) at the moment this batch tried to acquire it. No non-200 path exists in this handler.
**Public Interface:**
`export async function POST(): Promise<NextResponse>`
**Error Behaviour:** No try/catch in the route itself. Inside `runScheduledMatchingBatch` (M-017), each per-document `matchDocument()` call IS wrapped in `try { ... } finally { releaseMatchingLock(documentId); }` — so a failure matching one document releases that document's lock but does NOT get caught into `skipped`/`processed`; per M-017's source, an exception thrown by `matchDocument` inside the loop is NOT caught by an outer try/catch in `runScheduledMatchingBatch`, so it propagates out of the `for` loop entirely, aborting the batch for all remaining eligible documents and reaching this route unhandled -> 500. This means one bad document can silently prevent every subsequent eligible document in that batch run from being attempted, with no partial-success result returned to the caller (the whole request 500s instead of returning partial `processed`/`skipped` arrays).
**Known Fragility:** [NOTABLE — inbound integration point, IP-005] This module is the receiving endpoint for n8n's external trigger (IP-005) — an external system calls INTO this application here, the reverse direction of every other integration point in this codebase (which are this app calling out to Fabric/AI providers). Per `discovery/ID_REGISTRY.md`: "n8n... N/A — n8n calls this app (M-053), not the reverse." There is no idempotency key, rate limiting, or duplicate-trigger protection at the route level itself — protection against double-processing relies entirely on each document's own per-document lock in M-017 (`acquireMatchingLock`), which is the same lock M-047's manual Reconcile button uses; a manual Reconcile click racing against this scheduled batch on the same document is safely resolved by that shared lock (one gets `skipped`/409, not double-processed), per this route's own comment. As noted above, one throwing document aborts the entire batch with no partial-result reporting — a fragility a future engineer adding a new document type/edge case to the matching pipeline could easily reintroduce or worsen without realizing this route has no per-document error isolation of its own (M-017's `for` loop has no per-iteration try/catch around the throw itself, only the lock-release `finally`).
**Change Impact:** The sole invocation surface for the scheduled/batch matching path — no internal cron calls it (confirmed by A02: "no live timer/cron infrastructure invokes this in this build"). Any authentication requirement changes on `/api/matching` paths (matcher changes in M-043) directly affect whether n8n's external call can succeed. Shares matching-lock mechanics (`LOCK_STALE_AFTER_MINUTES`, `recon_document_lock`) with M-047 — a change to that lock's staleness window or table schema affects both routes' concurrency behavior identically.
**Callers:** External only — n8n (IP-005) calls this endpoint from outside the codebase; no internal M-NNN module calls it.
