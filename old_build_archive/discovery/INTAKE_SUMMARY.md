## System Purpose

VIVE Reconciliation is a Python-based AI-powered accounts payable automation tool for VIVE Collision, a multi-shop auto body repair company (~79 shops, Northeast US, growing toward 150). Vendor suppliers send monthly PDF statements; the system extracts line-item data from each PDF via Claude Sonnet 4.6, compares it deterministically against VIVE's ERP records (currently a mock generator, pending live NetSuite access), and surfaces discrepancies for a human AP team to review. It does not itself approve, reject, or execute any payment. Success looks like: every statement line either matches with high confidence or is correctly routed to human review — never silently misclassified either way.

## Known Architecture

- **Serving layer:** FastAPI + Jinja2, server-rendered (no client-side SPA). 10 routers: auth, dashboard, exceptions, jobs, reports, review_queue, upload, users, batches, intake_trigger.
- **Intake:** Manual upload (`POST /upload`) writes a PDF + a `jobs` row (PENDING) and returns immediately — extraction happens asynchronously. An Event Grid drop-zone webhook (`/api/intake-trigger`, `viverecondropzone`/`incoming-statements`) exists as a second intake path, code-complete with auth (shared secret, pinned container, 100-event cap) but not yet deployed — blocked on Azure RBAC permissions (Ashrith).
- **Worker pool:** 3 threads (`VIVE_WORKER_POOL_SIZE`) started at app boot, each polling `jobs` for PENDING rows every 30s and claiming atomically via `claim_next_pending_job()` (`UPDATE ... WHERE NOT EXISTS`, scoped per `pdf_filename` — not system-wide). A claimed job shells out to `scripts/run_full_pipeline.py` as a subprocess (30-min hard timeout), which runs all 4 notebook stages in sequence for that one file.
- **Extraction cache:** SHA-256 hash of PDF byte content, checked against `extraction_cache` before any AI call. Hit requires a prior run with `row_count > 0`. A cache hit skips extraction entirely — no AI call, no concurrency-slot acquisition.
- **Extraction:** Claude Sonnet 4.6 (Azure AI Foundry) reads the whole PDF directly, no per-vendor config, returns structured JSON. Gated by a cross-process, disk-based concurrency limiter (`VIVE_MAX_CONCURRENT_AI_CALLS`, default 2, file-lock semaphore in `lakehouse/ai_call_slots/`) — needed because each job runs in its own subprocess, so an in-process semaphore can't coordinate across workers. Fallback: `pdfplumber` + Tesseract OCR (local, no network, no semaphore), rows tagged `line_confidence = 0.50` (deliberately below the 0.60 gate).
- **Validation gate:** required fields present, numeric fields genuinely numeric, confidence ≥ 0.60, duplicate-within-batch check. Fail → `validation_document_review_queue` with reason logged, nothing silently dropped.
- **Bronze → Silver:** Bronze is raw/untyped (amounts as strings), one row per extracted line, tagged `source_file`/`statement_id`/`extraction_model`/`ingestion_timestamp`. Silver types everything, computes `invoice_number_normalized` for matching only (original retained separately, RULE-01), tags `record_source`, generates a stable `record_id` (SHA-256 of source+invoice+amount).
- **Reference side:** `02_generate_mock_erp.py` clones the Silver VENDOR_STATEMENT rows as the "ERP side" (mock, pending live NetSuite), applying deliberate mismatches from `config/mock_erp/scenario_config.json`, writes to Bronze/Silver tagged `INTERNAL_ERP`.
- **Matching engine:** 100% deterministic, zero AI. **Two** levels tried in order per vendor line, stopping at first success (verified directly against `src/matching/engine.py`, `MATCH_LEVEL_TO_TYPE = {1: "INVOICE", 2: "RO"}`): Level 1 — exact invoice number match, amount must also match within tolerance (an invoice match with a mismatched amount becomes an Amount Mismatch exception, not a lower level); Level 2 — RO number + amount, within tolerance. A third "fuzzy prefix" level was deliberately removed (RULE-11) after it silently cross-matched unrelated invoices whenever prefix and amount coincidentally lined up. Comparison uses the normalized invoice number; the match record stores the original. Deterministic confidence score per match type.
- **Gold:** matched rows → `gold_matched_invoices`; unmatched → `gold_exceptions` (reason code, `shop_owner`, `days_open` aging clock). Dashboard KPIs always live-query `gold_exceptions` directly (Claude.md Rule 3) — `gold_reconciliation_summary` is a snapshot table, historically prone to staleness after exception resolution (see Known Pain Points).
- **Report generation:** optional `--explain` narrative via Claude Haiku 4.5 (Azure Foundry), independent model from extraction's Sonnet, read-only summary layer.
- **Human review:** AP staff work `gold_exceptions` via the UI — Accept/Dispute/Write-off per row, or bulk-approve above a confidence threshold.
- **Backend:** `src/lakehouse/connection.py` selects SQLite (dev/test) or Azure SQL (prod) via `AZURE_SQL_SERVER` env var — the single place that knows. Schema changes are numbered migration files only, never hand-edited DDL.
